\section{Project Context}

The E-JUST Guest House (officially the University Guest Housing Booking System)
is an institutional accommodation platform for Egypt-Japan University of Science
and Technology. It provides a guest-facing booking portal and a dedicated
admin-only dashboard for managing the full lifecycle of room reservations.

This report focuses exclusively on the \textbf{Admin Dashboard} — the
management interface accessible only to authorised staff. It covers the
product scope, technical architecture, individual feature modules, data models,
API contract, and the decisions made during development.

\section{Goals and Scope}

The Admin Dashboard was designed to satisfy the following requirements:

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Unified overview} — a single-screen summary of all key metrics
        (total bookings, occupancy rate, revenue pipeline, pending approvals,
        today's check-in/check-out schedule) with animated visualisations.
  \item \textbf{Booking management} — list, search, filter, create, edit, and
        update the status of reservations; capture full guest contact details.
  \item \textbf{Room management} — view the room inventory and create new rooms
        with type classification and pricing.
  \item \textbf{Data export} — generate styled \texttt{.xlsx} workbooks for
        reservations, monthly booking counts, and revenue trends.
  \item \textbf{Real-time UX} — optimistic UI updates, smooth CSS transitions,
        and skeleton loading states throughout.
  \item \textbf{Adaptive theming} — full dark-mode and light-mode support with
        a shared brand colour scheme.
\end{enumerate}

\section{High-Level Architecture}

The system follows a classic client–server separation:

\begin{center}
\begin{tabular}{lll}
  \toprule
  \textbf{Layer} & \textbf{Technology} & \textbf{Responsibility} \\
  \midrule
  Frontend SPA & Vite + React\,18 + TypeScript & UI, state, routing \\
  API Client   & Axios + TanStack Query v5      & HTTP, caching, mutations \\
  Backend API  & FastAPI (Python\,3.11)          & Business logic, auth \\
  Database     & PostgreSQL (async SQLAlchemy)   & Persistence \\
  \bottomrule
\end{tabular}
\end{center}

The frontend is served on port \textbf{5173} (Vite dev server) and communicates
with the backend on port \textbf{8003} via a typed REST API. All admin routes are
mounted at the \texttt{/api/admin} prefix in the FastAPI application.

\section{Frontend Stack}

\begin{itemize}[leftmargin=2em]
  \item \textbf{Vite 5} — build tooling and dev server with HMR.
  \item \textbf{React 18} — component model, concurrent rendering.
  \item \textbf{TypeScript 5} — strict type safety across the entire codebase.
  \item \textbf{Tailwind CSS v3} — utility-first styling with \texttt{dark:}
        variants for adaptive theming. Custom design tokens (brand red
        \texttt{\#B30000}, glassmorphism helpers) defined in
        \texttt{tailwind.config.js}.
  \item \textbf{TanStack Query v5} — server-state management with
        optimistic updates, background refetch, and cache invalidation.
  \item \textbf{Axios} — HTTP client; instance configured with
        \texttt{VITE\_API\_BASE\_URL} from \texttt{.env}.
  \item \textbf{ExcelJS} — client-side \texttt{.xlsx} generation with full
        styling support (cell fills, borders, merged cells, freeze panes).
\end{itemize}

\section{Backend Stack}

\begin{itemize}[leftmargin=2em]
  \item \textbf{FastAPI} — async Python web framework; auto-generates OpenAPI
        docs at \texttt{/docs}.
  \item \textbf{SQLAlchemy 2 (async)} — ORM with \texttt{AsyncSession}; queries
        use Core \texttt{select()} style.
  \item \textbf{Pydantic v2} — request/response validation; \texttt{from\_attributes=True}
        enables direct ORM-to-schema conversion.
  \item \textbf{PostgreSQL} — relational database; enforces double-booking
        prevention via a native GiST exclusion constraint on room + date range.
  \item \textbf{Uvicorn} — ASGI server running the FastAPI application.
\end{itemize}

\section{Request Lifecycle}

A typical admin action (e.g.\ confirming a booking) follows this path:

\begin{enumerate}[leftmargin=2em]
  \item Admin clicks \emph{Confirm} in the UI.
  \item TanStack Query's \texttt{useMutation} fires \texttt{onMutate}: the
        local cache is updated immediately (optimistic UI).
  \item Axios sends \texttt{PATCH /api/admin/bookings/\{id\}/status} to the
        FastAPI backend.
  \item FastAPI validates the payload with Pydantic, calls
        \texttt{AdminRepository.update\_booking\_status()}, commits to
        PostgreSQL, and returns the updated \texttt{BookingResponse}.
  \item On success, \texttt{onSuccess} replaces the optimistic record with
        the server response; \texttt{onSettled} invalidates the bookings
        query to trigger a background refetch.
  \item On failure, \texttt{onError} rolls back the cache to the
        \texttt{snapshot} captured in \texttt{onMutate}.
\end{enumerate}

\begin{infobox}[title=Guest Contact Encoding]
  Because guest email and phone were added without a schema migration, they are
  encoded inside the existing \texttt{special\_requests} column using a
  pipe-delimited format:

  \begin{center}
    \texttt{Manual booking for guest: \{name\}|\{email\}|\{phone\}}
  \end{center}

  The backend helper \texttt{\_parse\_guest()} splits on \texttt{|} and is
  backward-compatible with old records that only contain the name segment.
  New records written by \texttt{\_encode\_guest()} always include all three
  fields (empty string when not provided).
\end{infobox}

\begin{tabular}{ll}

\subsection{Theming}

Tailwind's \texttt{dark:} variants are activated by toggling the \texttt{.dark}
class on the \texttt{<html>} element. Global overrides for light mode are
applied in \texttt{index.css} using the \texttt{html:not(.dark)} selector.

The design language is \emph{glassmorphism}: translucent card backgrounds
(\texttt{backdrop-blur}), subtle white/black border opacities, and a brand-red
(\texttt{\#B30000}) accent colour. Cards also feature a \textbf{cursor-tracked
border glow} via the \texttt{useGlowCard()} hook, which sets CSS custom
properties \texttt{--mx} / \texttt{--my} and a \texttt{::before} radial-gradient
pseudo-element.

\subsection{Booking Detail Modal}

A full-featured slide-in modal with smooth entry/exit animations:

\subsubsection{Animation Pattern}

The modal uses a \textbf{two-state animation trick} to ensure CSS transitions
always play from a hidden state, even when the component is freshly mounted:

\begin{enumerate}[leftmargin=2em]
  \item A \texttt{staleBooking} state preserves the last non-null booking so
        content remains visible during the close animation.
  \item A \texttt{visible} state lags one \texttt{requestAnimationFrame} behind
        \texttt{isOpen}, giving the browser one paint cycle to render the
        initial hidden state before applying transition classes.
  \item After close, a 320\,ms \texttt{setTimeout} clears \texttt{staleBooking},
        fully unmounting the DOM.
\end{enumerate}

\chapter{Known Limitations \& Future Work}
% =============================================================================

\section{Current Limitations}

\begin{itemize}[leftmargin=2em]
  \item \textbf{No authentication on admin routes} — the
        \texttt{/api/admin} endpoints accept requests without any token
        verification. This is intentional for the development phase but
        must be secured before production deployment.
  \item \textbf{Guest contact in \texttt{special\_requests}} — email and phone
        are stored using a pipe-encoded string rather than dedicated columns.
        A future schema migration should add proper \texttt{guest\_email} and
        \texttt{guest\_phone} columns to the \texttt{bookings} table.
  \item \textbf{No pagination UI} — the API supports \texttt{skip}/\texttt{limit}
        parameters but the frontend fetches all records in one request.
  \item \textbf{No room editing or deletion} — the Rooms page only supports
        creation. Edit and soft-delete actions are not yet implemented.
  \item \textbf{No date-range filter on bookings} — search is limited to guest
        name and status; filtering by check-in period is not available.
\end{itemize}

\section{Recommended Future Enhancements}

\begin{enumerate}[leftmargin=2em]
  \item Add JWT/session authentication to all \texttt{/api/admin} routes,
        enforcing the \texttt{role = 'admin'} check.
  \item Migrate guest contact fields to proper database columns with a
        SQLAlchemy/Alembic migration.
  \item Implement server-sent events or WebSocket push for real-time booking
        notifications.
  \item Add a printable/PDF booking confirmation generator.
  \item Introduce server-side pagination and date-range filtering.
  \item Add room editing and soft-delete (toggle \texttt{is\_active}).
  \item Internationalise the interface (Arabic/English switcher).
\end{enumerate}

\chapter{Conclusion}
% =============================================================================

The E-JUST Guest House Admin Dashboard delivers a complete administrative
interface built on modern web standards. The combination of React\,18's
concurrent model, TanStack Query's server-state primitives, and FastAPI's
async I/O produces a responsive, reliable experience with predictable
optimistic updates and graceful error handling.

The visual design — glassmorphic cards, animated statistics, cursor-tracked
glows, and a brand-red accent — reflects the E-JUST institutional identity
while meeting contemporary SaaS dashboard expectations. Full light/dark mode
support and accessible colour contrast ratios ensure the interface is usable
across a range of display environments.

The Excel export system, powered entirely by ExcelJS in the browser, produces
professionally styled \texttt{.xlsx} workbooks that operational staff can
immediately use for record-keeping, auditing, and reporting — without any
server-side rendering overhead.

The codebase is structured for maintainability: strict TypeScript types
throughout, a clean hook/component separation, and a thin API client layer
that isolates HTTP concerns from UI logic. Future work — authentication,
server-push notifications, pagination, and a proper guest contact schema
migration — can be layered onto this foundation without architectural changes.
